# Extended Query Protocol PostgreSQL

Живой конспект протокола для Mpgsql. Документ описывает роли и поток сообщений. Побайтовые правила, startup,
authentication и API реализованного слоя сообщений описаны в [protocol-messages.md](protocol-messages.md).

## Контекст версии

PostgreSQL 18 описывает актуальную версию frontend/backend protocol 3.2. Для обратной совместимости со старыми серверами
и middleware библиотека libpq по умолчанию обычно запрашивает версию 3.0.

Кодек Mpgsql использует **3.0**: `StartupMessage` передаёт `196608`, `BackendKeyData` содержит PID и 32-битный secret
key, а `CancelRequest` имеет длину 16 байт. Разбор `NegotiateProtocolVersion` сам по себе не включает поддержку другой
версии. Перед переходом на 3.2 нужно отдельно реализовать и проверить отличающиеся форматы.

Чтение backend frames проверяет структуру и границы сообщений без отдельной
валидации UTF-8. Строки декодируются строгим UTF-8 decoder только при обращении
к typed accessor; ошибочная кодировка отклоняется в этой точке. Сырые UTF-8
payloads конвертеров передаются без сканирования содержимого. Ошибку значения
при записи возвращает PostgreSQL; восстановление по-прежнему требует `Sync`
и `ReadyForQuery`.

## Что такое Extended Query

Extended Query разделяет обработку SQL на три этапа:

1. `Parse` создаёт prepared statement из текста запроса.
2. `Bind` связывает prepared statement с параметрами и создаёт готовый к выполнению portal.
3. `Execute` выполняет portal полностью или частично.

Серия extended-query сообщений завершается `Sync`: это точка синхронизации и восстановления после ошибок, на которую
сервер отвечает `ReadyForQuery`.

Для binary `bigint[]` Mpgsql предоставляет [LongArrayConverter](long-array-converter.md)
для `ReadOnlyMemory<long>`. Он кодирует array payload; внешний length и binary format
принадлежат Bind/DataRow. SQL NULL всего массива остаётся nullable field внешнего сообщения.

Реализован [helper для отправки запросов и чтения результатов](query-helpers.md).
Отправку и чтение крайне рекомендуется вести параллельно. `SendQueryAsync`
ставит Parse/Bind/Describe/Execute без Sync; отдельный `SendSyncAsync`
вызывается producer после всех отправок. `ReadResultsAsync` и dispose ничего
не отправляют. Группы разделяют Sync/error/transaction boundary, а несколько
закрытых групп могут находиться в полёте на одном соединении.

Writer объединяет уже стоящие в очереди сообщения в один transport `FlushAsync`,
ограничивая одну отправку 64 КиБ или 256 сообщениями. Большой отдельный packet
не дробится этим ограничением. Writer не ждёт появления `Sync`: одиночный
`SendQueryAsync`, которого ожидает producer, также отправляется. Каждая send
operation подтверждает общий flush; логическая отмена опубликованного query
может раньше освободить его входные буферы. Объединение transport flush не
меняет wire-порядок, явные `Sync` и соответствующие `ReadyForQuery` границы.

Внутренний producer `MpgsqlBatch` предварительно проверяет все команды и
использует одно подтверждение освобождения входных буферов для всей группы.
Подтверждение включает каждую принятую команду, в том числе отменённую во время
кодирования. Доставка `Sync` подтверждается отдельно. Raw sends сохраняют
индивидуальные подтверждения; границы протокола и `QueryIndex` общие для обоих
путей. ADO.NET-команда и batch блокируют изменение параметров до полного
завершения выполнения и сохраняют типизированное хранилище для повторных
запусков. Подтверждение producer означает, что транспорт больше не обращается
к входным буферам; оно само по себе не завершает ADO.NET-операцию.

Reader ожидает очередь результатов напрямую. Очередь допускает параллельный
drain при отмене, передаёт владение каждой строкой одному потребителю и
освобождает строки, оставшиеся при Dispose. Уведомления ожидающему reader
выполняются асинхронно. Backpressure по байтам строк остаётся на уровне session.

Session переиспользует последнее декодированное `RowDescription` и строку
`CommandComplete` при полном совпадении соответствующих backend payloads.
Для сравнения сохраняется собственная копия wire bytes размером до 4096 и
1024 байт соответственно; более крупные payloads декодируются обычным путём.
Это ограниченное переиспользование полученных метаданных: `Describe` отправляется
для каждого запроса, SQL не служит ключом. Массивы `Columns` и строки тегов не
возвращаются в pool и не изменяются при замене сохранённого значения, поэтому
захваченные reader метаданные сохраняют своё время жизни.

### Явные prepared statements в helper

`MpgsqlMessageSession.CreatePreparedStatement` создаёт локальный объект с SQL,
принадлежащий одной физической сессии, и копирует полный список ненулевых OID.
`SendPrepareAsync(statement)` внутри batch отправляет именованный `Parse`;
`statement.Prepared` подтверждается `ParseComplete`. Повторный
`SendQueryAsync(statement, parameters)` отправляет только
`Bind(statement)` → `Describe(portal)` → `Execute` с binary formats и
безымянным portal. `Sync` всегда явно отправляет producer, в том числе перед
ожиданием `Prepared`. В batch подготовки выполнения можно поставить сразу
после Parse; в других batch — после его успешного подтверждения.

Подготовка и `SendCloseAsync(statement)` являются отдельными операциями в FIFO
ответов: они не создают результатов и не увеличивают `QueryIndex`. Принятый
Close запрещает новые выполнения, сохраняя ранее принятые отправки. Закрытие
подтверждается `CloseComplete`; отменённый или пропущенный Close можно повторить
в новом batch после завершения прежней границы Sync. Named statement сохраняется
до Close или конца серверной сессии; уже полученный ParseComplete не отменяется
ошибкой последующего выполнения. Неподтверждённые/пропущенные подготовки
завершаются ошибкой после ReadyForQuery. Автоматических повторов, SQL-кеша
и вывода типов нет. Подробные API и примеры — в
[query-helpers.md](query-helpers.md#явные-prepared-statements).

Локальный lifecycle не отправляет сообщений: до admission `SendPrepareAsync`
session учитывает handles слабо, поэтому abandoned handles, SQL и OID собираются GC.
`Dispose()` допустим для ещё не поставленного Parse, неуспешной подготовки,
подтверждённого Close или остановленной session. Pending/успешная подготовка
требует явного server Close и подтверждения; Dispose до этого бросает исключение.
Сильное удержание начинается при admission Parse. Отменённый до публикации Parse
освобождается сразу, failed/skipped Parse — после Sync/ReadyForQuery; Close такого
handle ничего не отправляет. Полученный ParseComplete сохраняет удержание до
CloseComplete или остановки session, в том числе после логической отмены запроса.

## Сообщения и их назначение

### Frontend → backend: основные команды

| Сообщение              | Роль                                                                | Связанный объект или эффект                                                                          |
|------------------------|---------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| `Parse`                | Передаёт один SQL-запрос и, при необходимости, типы параметров.     | Создаёт именованный или безымянный prepared statement.                                               |
| `Bind`                 | Передаёт значения и форматы параметров, а также форматы результата. | Создаёт именованный или безымянный portal на основе prepared statement.                              |
| `Describe` (statement) | Запрашивает типы параметров и описание будущего результата.         | Prepared statement; ответы: `ParameterDescription`, затем `RowDescription` или `NoData`.             |
| `Describe` (portal)    | Запрашивает описание результата, который вернёт portal.             | Portal; ответ: `RowDescription` или `NoData`.                                                        |
| `Execute`              | Запускает portal; может ограничить число возвращаемых строк.        | Portal; при частичном выполнении сервер отвечает `PortalSuspended`.                                  |
| `Close` (statement)    | Освобождает prepared statement.                                     | Также закрывает созданные из него открытые portals; обычно подтверждается `CloseComplete`.           |
| `Close` (portal)       | Освобождает portal.                                                 | Обычно подтверждается `CloseComplete`.                                                               |
| `Flush`                | Требует немедленно отправить уже накопленные сервером ответы.       | Сам по себе не порождает отдельного ответа; нужен, если клиент хочет прочитать результаты до `Sync`. |
| `Sync`                 | Завершает серию сообщений и задаёт точку ресинхронизации.           | После обработки сервер отправляет `ReadyForQuery`.                                                   |

### Backend → frontend: ответы по роли

**Подтверждения этапов**

- `ParseComplete` — `Parse` успешно завершён.
- `BindComplete` — `Bind` успешно завершён и portal создан.
- `CloseComplete` — `Close` успешно обработан.

**Метаданные**

- `ParameterDescription` — OID типов параметров prepared statement.
- `RowDescription` — описание столбцов строк результата.
- `NoData` — описываемый statement или portal не возвращает строки.

**Данные и завершение выполнения**

- `DataRow` — одна строка результата; сообщений может быть ноль или больше.
- `CommandComplete` — SQL-команда выполнена полностью.
- `EmptyQueryResponse` — portal создан из пустого запроса.
- `PortalSuspended` — достигнут заданный в `Execute` лимит строк; выполнение можно продолжить новым `Execute` того же
  portal.

**Границы цикла и ошибки**

- `ReadyForQuery` — сервер обработал `Sync` и снова готов к новому циклу; сообщение также содержит состояние транзакции.
- `ErrorResponse` — ошибка обработки сообщения. Клиент должен перейти к восстановлению через `Sync`.
- `NoticeResponse` — предупреждение или уведомление, не заменяющее ожидаемый основной ответ; клиент должен быть готов
  принять его и продолжить обработку.

### Асинхронные и смежные сообщения

Это не основные команды Extended Query, но драйвер обязан корректно принимать их в соответствующих состояниях:

- `ParameterStatus` — сообщает об изменении параметра сеанса; может появляться асинхронно.
- Семейство COPY образует отдельный подпротокол: `CopyInResponse`, `CopyOutResponse`, `CopyBothResponse` переключают
  соединение в соответствующий режим; `CopyData` переносит данные; `CopyDone` завершает передачу; `CopyFail` позволяет
  frontend аварийно завершить copy-in.

#### Binary COPY

Реализованы [binary COPY codec, framing и состояние операции](binary-copy.md).
`BinaryCopyOperation` резервирует логическое состояние COPY отдельно от DataRow:
данные → CopyDone → CommandComplete → ReadyForQuery, либо ErrorResponse → recovery.
Физическое соединение должно оставаться выделенным COPY до этого ReadyForQuery;
другие multiplexed запросы планируются на другие соединения либо ждут завершения.

В Extended COPY IN отправляй **новый Sync после завершения COPY data phase** и
отмечай его через `SyncSent`. Sync/Flush, пришедшие во время COPY IN, сервер
игнорирует; такой ранний Sync не заменяет границу восстановления. CopyFail или
серверная ошибка завершают data phase и требуют ErrorResponse/Sync/ReadyForQuery.
Для COPY OUT Sync можно заранее поставить после Execute, отметив его через
`SyncSent` после получения CopyOutResponse; также допустима отправка после CopyDone.
Для Simple Query ReadyForQuery приходит без Sync. NoticeResponse, ParameterStatus
и NotificationResponse маршрутизируются независимо и не меняют COPY state.
COPY BOTH/replication этой реализацией не поддерживается.

#### `NOTIFY` и `NotificationResponse`

Команда `LISTEN channel` регистрирует текущую сессию как слушателя канала. После успешной фиксации
`NOTIFY channel, payload`, выполненного другой или этой же сессией, сервер отправляет слушающему соединению
backend-сообщение `NotificationResponse`. Это сообщение имеет тип `A` и содержит PID уведомляющего backend-процесса, имя
канала и строковый payload.

`NotificationResponse` не является ответом на конкретную команду Extended Query и не завершает ожидаемый цикл `Parse`,
`Bind`, `Execute` или `Sync`. Драйвер должен распознать его в общем цикле чтения, передать уведомление в отдельный поток
событий или очередь, а затем продолжить разбор ответа, который ожидался до уведомления. Выполнять пользовательский
обработчик синхронно внутри сетевого reader loop нельзя: медленный callback остановит чтение всего соединения. Это
архитектурное следствие для Mpgsql, а не требование wire protocol.

Текущая реализация PostgreSQL отправляет `NotificationResponse` только вне транзакции, поэтому сообщение не появляется
посреди command-response series, но может прийти непосредственно перед `ReadyForQuery`. Официальная рекомендация всё
равно требует уметь принять его в любой точке протокола. Даже когда соединение простаивает, драйвер должен продолжать
чтение: иначе уже доставленное по сети уведомление останется в сокетном буфере до следующего чтения. При этом `NOTIFY`
не является долговременной (durable) очередью, поэтому драйвер не должен обещать гарантированное хранение или доставку
уведомлений.

`NotificationResponse` сообщает о событии канала `LISTEN`/`NOTIFY`; `NoticeResponse` передаёт предупреждение или
информационное сообщение сервера. Их нужно маршрутизировать независимо.

Startup, negotiation и authentication — отдельные фазы соединения и в классификацию Extended Query здесь не включены.

## Типовая последовательность

Для запроса с описанием portal типовой поток выглядит так:

`Parse` → `ParseComplete` → `Bind` → `BindComplete` → `Describe` → (`RowDescription` или `NoData`) → `Execute` →
`DataRow`* → (`CommandComplete` или `PortalSuspended`) → `Sync` → `ReadyForQuery`.

Если описывается prepared statement, перед `RowDescription` или `NoData` сервер также отправляет `ParameterDescription`.
`Execute` сам по себе не отправляет `RowDescription` и `ReadyForQuery`. `Flush` отправляют после команды, когда клиенту
нужно получить накопленные ответы до отправки `Sync`.

## Ошибочная ветка

Если при обработке extended-query сообщения возникает ошибка, сервер отправляет `ErrorResponse`, затем читает и
пропускает последующие extended-query сообщения до `Sync`. После `Sync` сервер отправляет `ReadyForQuery` и возвращается
к обычной обработке. Поэтому клиент должен уметь отбросить ожидаемые подтверждения пропущенных команд и восстановить
состояние по паре `Sync` / `ReadyForQuery`.

При terminal failure этой границы может не быть. `FATAL`/`PANIC` завершают session
с received diagnostics сразу, включая idle session. Обрыв transport после
`ErrorResponse`, но до `ReadyForQuery`, также сохраняет диагностику и причину
обрыва. `MpgsqlServerException.TransactionStatus` в этом случае равен `null`:
ошибка завершения не подтверждает восстановление группы или статус транзакции.
Все незавершённые группы получают terminal failure, а transport исключается из
повторного использования. После принятого `ReadyForQuery` диагностика ошибки
группы очищается и не переносится на следующий обрыв.

См. [Error and Notice Message Fields](https://www.postgresql.org/docs/17/protocol-error-fields.html)
и [Termination](https://www.postgresql.org/docs/17/protocol-flow.html#PROTOCOL-FLOW-TERMINATION).

## Верхний API

Сообщения и парсеры протокола находятся в независимом проекте и NuGet-пакете `Mpgsql`.
Сессии, TCP/TLS, аутентификация, query helpers, prepared handles и result buffers
находятся в `Mpgsql.Sessions`, который ссылается на `Mpgsql`. ADO.NET и эксклюзивный
пул находятся в `Mpgsql.Client`; независимые запросы и автоматический shared-Sync
планировщик — в `Mpgsql.Multiplexing`. Два верхних проекта ссылаются на Sessions
и не зависят друг от друга. Пространства имён низкоуровневых сущностей сохранены.

Верхний API явных подключений и мультиплексирования описан в [upper-api.md](upper-api.md).
По умолчанию его отправляющий поток ставит Sync для каждого принятого выполнения. Низкоуровневые
SendQueryAsync, ReadResultsAsync и освобождение объектов по-прежнему не создают Sync.
Батч отправляется и читается параллельно; раннее освобождение reader пропускает результаты,
сохраняя отправку принятых команд. Повторное использование транспорта требует ReadyForQuery,
а отмена при явном подключении — также завершения отправки CancelRequest. Отмена запроса
на мультиплексере остаётся логической и не отправляет CancelRequest.
Отменённый вызов DataSource ждёт прекращения доступа producer/encoder к входным
параметрам, но не ждёт заблокированный flush SQL или Sync. Отправка обязательного
Sync и чтение до ReadyForQuery продолжаются в фоне и удерживают scheduling slot.
Отмена во время encoding не освобождает borrowed inputs до завершения encoding;
request token не подменяет lifetime token общего транспорта при FlushAsync.

Для прямых вызовов `MpgsqlMultiplexingDataSource` есть отдельный opt-in режим `SyncGroupSize > 1`.
Физическая сессия ставит общий Sync после N принятых запросов либо по
`SyncGroupTimeout` от первого запроса группы; новые поступления не продлевают
таймер. Чтение клиента не запускает Sync и не требуется для срабатывания таймера.
Запросы сохраняют отдельные readers и локальный QueryIndex = 0, но заканчивают
протокол только на общем ReadyForQuery. Лимит in-flight считает логические запросы,
а row budget и backpressure продолжают действовать на всю физическую сессию.

Общий Sync означает общую error/implicit-transaction boundary. При SQL error
ошибочный запрос получает MpgsqlServerException, остальные — MpgsqlSyncGroupException
с исходной причиной и признаком WasSkipped. Уже полученный CommandComplete не
подтверждает commit до общей границы; ранее выполненный запрос тоже получает ошибку.
Пропущенные команды не повторяются автоматически. Полное выполнение может быть
неатомарным для команд, которые PostgreSQL завершает отдельным commit.
Логическая отмена отбрасывает только свой поток строк, не отменяет SQL соседей
и не подавляет общий Sync. Явные connections/batches и raw API сохраняют прежние границы.

Таймер ограничивает время до постановки Sync, а не гарантирует время его доставки:
writer, backpressure и планировщик ОС могут задержать отправку. Протокольный Flush
на каждый запрос не добавляется. Сервер вправе буферизовать ответы до Sync;
клиентский PipeWriter.FlushAsync не заменяет PostgreSQL Flush (`H`). Проверка режима
включает реальный PostgreSQL, в том числе откат предшествующего INSERT после ошибки
соседа, пропущенную команду, отмену и drain большого результата.

Сессии DataSource ограничивают объём удерживаемых строк; самостоятельные низкоуровневые
сессии сохраняют прежний контракт буферизации. Очистка выбранного серверного состояния
вызывается явно, не выполняется при возврате подключения и не удаляет prepared statements.
За привязку к backend внешнего pooler отвечает клиент.

Receive loop объединяет уведомления в пределах ответа команды: CommandComplete
пробуждает ожидающего reader. Частичный ответ пробуждает reader в конце текущего
чтения PipeReader. События доступны для чтения сразу; откладывается только
пробуждение уже ожидающего consumer. ReadyForQuery завершает группу и
пробуждает её reader, не скрывая накопленные результаты. Если row budget заполнен,
уведомление выполняется до ожидания освобождения строк. Дополнительного чтения,
таймера или ожидания Sync для выдачи частичного ответа нет; continuations consumer
не исполняются синхронно на receive loop.

Внутренний receive путь проверяет длину frame и количество полей DataRow, а затем
проверяет длины значений при построении компактного индекса уже удерживаемой строки.
Отбрасываемые строки проверяются без индекса. Публичный BackendMessageReader
по-прежнему проверяет весь payload перед возвратом. Индекс хранит Int32 offsets;
сам payload копируется в непрерывное хранилище или передаётся из frame assembly.
Пустые внутренние хранилища переиспользуются с пределом 1024 на сессию; payload и
индекс возвращаются владельцу/ArrayPool при каждом освобождении. Поколение lease
защищает новую строку от повторного освобождения старого handle. Низкоуровневые
batch и reader остаются одноразовыми. ADO.NET-команды и `DbBatch` можно менять и
повторно выполнять после полного завершения предыдущего выполнения.
